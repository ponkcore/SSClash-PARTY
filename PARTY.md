# SSClash PARTY downstream policy

SSClash PARTY is an independent downstream of
[`zerolabnet/SSClash`](https://github.com/zerolabnet/SSClash). It preserves
the original GPL-2.0 license, copyright notices, package name, and upstream
attribution. It is not an official ZeroChaos build.

## Why this downstream exists

The initial PARTY delta added a supported workflow for complete Mihomo
profiles generated by providers and control panels such as Remnawave. PARTY's
second revision generalizes that workflow into three configuration sources:
adaptive subscriptions, local proxy links combined with trusted templates,
and complete manual YAML. See
[Configuration sources](docs/configuration-sources.md).

Unlike a node-only `proxy-provider`, a complete remote profile can update the
entire policy graph: nodes, groups, rule providers, ordered rules, and their
relationships. Users who do not want remote policy can force a PARTY template
and import only nodes/providers.

The downstream keeps router integration under local control. A remote profile
cannot silently replace the transparent listener, routing mark, controller
authentication, dashboard path, DNS listener, or selected DNS interception
mode. Every update is parsed, tested, applied atomically, health-checked, and
rolled back on failure.

See [the managed full-profile design](docs/managed-full-profile.md) for the
exact trust boundary and recovery behavior.

## Compatibility contract

The OpenWrt package remains named `luci-app-ssclash`. This allows an existing
SSClash installation to be upgraded without creating two services that fight
over the same firewall, DNS, controller, and `/opt/clash` paths.

PARTY packages are architecture-specific because they contain a compiled Go
profile merger. Never install an artifact merely because the router CPU is
described as “ARM64” or “x86-64.” Match all of:

- OpenWrt release line;
- target and subtarget;
- package architecture from `/etc/openwrt_release`;
- package format: APK for OpenWrt 25 or IPK for supported older releases.

Release artifacts are independent builds. Verify the adjacent SHA-256 file
before installation.

## Branch contract

- `main` is a clean fast-forward mirror of `upstream/main`.
- `feature/*` contains isolated, reviewable downstream work.
- `party` contains tested downstream releases.

Upstream changes are first mirrored into `main`, then merged into a temporary
integration branch based on `party`. The integration branch must pass the
quality and package matrix before it advances `party`.

The detailed procedure is in
[Upstream synchronization](docs/upstream-sync.md).

## Release contract

PARTY release tags use the form:

```text
v<upstream-version>-party.<downstream-revision>
```

The OpenWrt package keeps the upstream version and increments
`PKG_RELEASE`, so the first managed-profile preview is:

```text
Git tag:         v4.7.0-party.1
OpenWrt package: luci-app-ssclash 4.7.0-r2
```

The configuration-source revision is:

```text
Git tag:         v4.7.0-party.2
OpenWrt package: luci-app-ssclash 4.7.0-r3
```

The package-upgrade lifecycle correction is:

```text
Git tag:         v4.7.0-party.3
OpenWrt package: luci-app-ssclash 4.7.0-r5
```

It accounts for OpenWrt APK stopping packaged init scripts before the new
pre-upgrade script can observe their runtime state. Services enabled at boot
are resumed, the subscription updater follows its UCI enable switch, and
disabled services remain disabled after the legacy recovery boundary. PARTY.1
and PARTY.2 get a one-time managed-subscription fallback because those package
revisions could lose the Clash boot link during an upgrade. Package release r4
was an internal live validation build and was never published; r5 also fixes
first-install detection when OpenWrt starts the new init script before the
custom post-upgrade migration runs.

A release is published only after:

- Go unit, race, vet, and lint checks pass;
- OpenWrt shell, LuCI JavaScript, and ACL checks pass;
- the source tree passes secret scanning;
- APK/IPK packages build in the declared matrix;
- extracted package architecture, permissions, and required files are
  verified;
- every artifact receives a SHA-256 sidecar.

## Upstream relationship

General bug fixes should be proposed upstream when possible. The managed
full-profile feature may also be proposed upstream as a focused pull request.
If upstream accepts and maintains equivalent behavior, PARTY should consume
the upstream implementation and retire duplicate patches.

Do not report PARTY-specific packaging or profile-sync failures as upstream
SSClash bugs without first reproducing them on an official upstream release.

## Private data

Never publish:

- subscription URLs or tokens;
- Remnawave HWIDs;
- controller secrets;
- proxy credentials or raw generated YAML;
- router passwords, SSH keys, public IP addresses, or configuration backups.

The repository, CI logs, issues, and release notes must contain only redacted
structural diagnostics.
